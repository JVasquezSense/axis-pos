# Plan: Borrado en cascada de tenants + sistema de planes con features restringidas

## Problemas a resolver
1. **Borrar tenant no elimina las cuentas (User)**: `UserProfile.tenant` usa `CASCADE` (borra el perfil), pero el `User` de Django queda huérfano. Hay que borrar también los usuarios.
2. **Sistema de planes con features**: hoy `features` es un JSON suelto por tenant, sin modelo de Plan, sin límite de usuarios, y el frontend **no hace cumplir** las features en la barra lateral (solo usa `ROLE_NAV`).

## Decisiones de diseño (asumidas, sin respuesta del usuario)
- **Modelo de planes**: Planes predefinidos (Básico/Pro/Enterprise) como plantillas de features + límite de usuarios, con **override por tenant** (el admin puede personalizar features individuales por restaurante). Así hay plantillas reutilizables + flexibilidad.
- **Módulos restringibles**: todos los del `TenantFeatures` actual (pos, kitchen, inventory, recipes, salon, reservations, crm, suppliers, employees, reports, website, web_orders) + 3 nuevos toggles (qr, whatsapp, ai) + `maxUsers` (límite de usuarios).

## Cambios

### 1. Backend — Fix borrado en cascada
**Archivo**: `api/views.py` (`AdminTenantViewSet.perform_destroy`)

Sobrescribir `perform_destroy` para que al borrar un tenant se eliminen también los `User` asociados (vía sus `UserProfile`). Hoy no existe `perform_destroy`, así que usa el default que solo borra el `Tenant` (y los perfiles por CASCADE, pero deja los Users huérfanos).

```python
def perform_destroy(self, instance):
    # Borra las cuentas de usuario (User) vinculadas a este tenant.
    from django.contrib.auth import get_user_model
    User = get_user_model()
    user_ids = list(UserProfile.objects.filter(tenant=instance).values_list("user_id", flat=True))
    with transaction.atomic():
        super().perform_destroy(instance)  # borra tenant + datos por CASCADE
        User.objects.filter(id__in=user_ids).delete()  # borra las cuentas
```

### 2. Backend — Modelo Plan + features ampliadas
**Archivo**: `api/models.py`

- Nuevo modelo `Plan` (tabla `api_plan`) con: `code` (starter/growth/enterprise), `name`, `max_users`, `features` (JSON con defaults de cada plan). No se borra con el tenant (es configuración global del SaaS).
- `Tenant`: ampliar el campo `features` para incluir `qr`, `whatsapp`, `ai` y `max_users` (estos dos últimos viven en features para override por tenant).
- `_default_features()`: ampliar a 15 toggles + `max_users`.
- Defaults por plan:
  - **Básico (starter)**: pos, kitchen, salon, menu. `max_users: 2`. Sin QR/WhatsApp/IA/web/inventario/recetas/CRM/reportes.
  - **Pro (growth)**: todo lo de Básico + inventory, recipes, crm, reports, suppliers, web_orders, qr. `max_users: 8`.
  - **Enterprise**: todo activado + whatsapp, ai, website, employees, reservations, audit. `max_users: 50`.
- Migración nueva + seed de los 3 planes.

### 3. Backend — Hacer cumplir las features (middleware/permisos)
**Archivo**: `api/views.py`

- Función helper `tenant_features(tenant)` que devuelve el dict de features efectivas (override del tenant o defaults del plan).
- Cada ViewSet de negocio que tenga un toggle (ej: `/inventory/`, `/recipes/`, `/returns/`, `/whatsapp/*`) añade un check en `get_queryset`/`perform_create`: si la feature está desactivada para el tenant → devuelve queryset vacío / 403.
- `AdminTenantViewSet.users` (POST crear usuario): respetar `max_users` del tenant → 403 si se excede.
- `PublicOrderView` (pedido web): si `web_orders` desactivado → 403.
- Endpoint `/public/<slug>/menu/`: no devolver el botón de QR si la feature está off (campo `qrEnabled` en la respuesta).

### 4. Backend — Exponer features en /auth/me/ y /admin/tenants/
**Archivo**: `api/views.py` (`MeView`) y `api/serializers.py`

- `MeView` añade `tenantFeatures` (dict de features efectivas) y `tenantMaxUsers`.
- `TenantAdminSerializer` añade `maxUsers` (resuelto del plan/override).
- Nuevo endpoint `GET /admin/plans/` para listar los 3 planes y sus features (para la UI de configuración).
- `AdminTenantViewSet.update_features` sigue igual (override por tenant).

### 5. Frontend — Barra lateral restringida por features
**Archivos**: `src/store/auth.store.ts`, `src/layouts/sidebar.tsx`, `src/lib/nav.ts`

- `auth.store`: añadir `tenantFeatures: Record<string, boolean>` y `tenantMaxUsers: number`, poblados desde `/auth/me/` (o decodificados del JWT). El login ya trae estos datos.
- `nav.ts`: añadir un campo `feature?` a cada `NavItem` que mapee al toggle correspondiente (ej: `inventory` → feature `inventory`, `kds` → feature `kitchen`, `returns` → feature `inventory`, `website` → feature `website`, `salon` → feature `salon`, etc.).
- `sidebar.tsx`: el filtro pasa de `NAV_ITEMS.filter(i => allowed.includes(i.key))` a filtrar **también** por `!i.feature || tenantFeatures[i.feature]`. Así un item solo aparece si el rol lo permite Y la feature del plan está activa.
- El superadmin (`/admin`) no se restringe por features (gestiona todo).

### 6. Frontend — Admin: UI de planes y features
**Archivo**: `src/app/(app)/admin/page.tsx`, `src/services/saas.service.ts`

- Ampliar `TenantFeatures` (type) con `qr`, `whatsapp`, `ai`, `maxUsers`.
- Ampliar `FEATURE_LIST` con los 3 toggles nuevos + mostrar `maxUsers` como input numérico.
- Al crear/editar un tenant: al elegir un `plan`, precargar las features default de ese plan (consulta `/admin/plans/`), permitiendo override posterior.
- `TenantUsersDialog`: al crear usuario, mostrar contador `X / maxUsers` y bloquear si se excede el límite.

### 7. Frontend — Storefront web respeta QR desactivado
**Archivo**: `src/app/restaurant/[slug]/page.tsx`

- El endpoint `/public/<slug>/menu/` ya devolverá `qrEnabled`. Si está off, la carta no muestra el banner de mesa (aunque igual permite pedidos web genéricos).

## Migraciones y datos
- `0017_plan_tenant_features` (nueva): modelo Plan + nuevos campos en features (son JSON, no requieren columna nueva).
- Seed de los 3 planes en `seed.py` o `0018_seed_plans`.

## Verificación
1. **Borrado en cascada**: borrar un tenant → sus `User` ya no existen (login falla con ese email).
2. **Barra lateral**: un tenant con plan Básico solo ve POS/Cocina/Salón/Menú; uno Enterprise ve todo. Cambiar plan → la barra se actualiza tras re-login.
3. **Límite de usuarios**: un tenant Básico (max 2) no puede crear un 3er usuario (403).
4. **Features enforced backend**: con `inventory` off, `/inventory/` devuelve [] y no permite crear items.
5. **QR off**: el storefront no muestra el banner de mesa.
